## 02:00 — `refined` becomes a dispatch gate: five decisions, three tickets

Steve raised four improvements to refinement; grilling them changed two.

**The grounding is the part worth keeping.** `refined` gated **nothing** — the queue gate was `ready`
(the four-section body check, D-058) plus the D-051 blocker gate. And `needsQueueBypass` is
**client-side only**: the server's `updateTicket` never checked `ready`, so a `curl` PATCH — and
`approveRefine`'s own "Approve & queue" — already put an unformatted robot ticket in the Queue.
**10 tickets of 634 were refined.**

**The migration window was open**: the Queue held one ticket (PD-611, assignee `steve`) and **zero**
robot-assigned tickets, so adding `refined = 1` to `robotQueueCandidates` stranded nothing. It stops
being free the moment anything is queued.

Decisions:

1. **Hard gate on the ticket AND its Epic, no bypass.** `ready` keeps its bypass — "run it
   unformatted anyway" is a real want; "dispatch work nobody has read" is not.
2. **One shared predicate, three layers.** `queueBlockers()` in `packages/shared` beside `isReady`,
   returning an ordered criteria list. Route guard refuses and returns it; the web renders the same
   function's output; the loop query adds `refined = 1` as a backstop for the one case the guard
   cannot catch — a ticket un-refined *after* queueing.
3. **Refine children: agent declares, server verifies.** `refined` defaults true per child, downgraded
   if a robot-assigned child's body fails `isReady`. Human-assigned children skip that test.
4. **No fourth Epic state** — "refined but its members aren't" is derived, never stored.
5. **A Populate marks the Epic refined, because it now rewrites the Epic body.** Steve's synthesis,
   which dissolved my objection that auto-marking asserts "the description frames the work" on a body
   nobody rewrote.

**The argument that settled #4, because it will come up again:** auto-marking an Epic refined once
its last member is refined **defeats D-089's invalidation** — add a member → un-refines; refine that
member → silently re-refines, and the human never sees the invalidation the mechanism exists to
raise. Steve's stated instinct was the auto-mark; the argument reversed it. #5 is not the same thing:
that one is the Refine session itself, where the claim originates.

**The ordering trap, before it bites a third time:** `createTicket` fires `invalidateEpicRefinement`
per joining member, so a Populate must mark the Epic refined **last**. This exact bug was hit while
building PD-610 — in a test fixture, which is the only reason it was caught.

Filed under PD-493 ([Epic] Task Tracker board — views & interactions): **PD-632** (gate the Queue on
refinement), **PD-633** (the criteria-checklist refusal modal; `PD-632 blocks PD-633`), **PD-634**
(a Refine session's output is born refined). Amended **PD-611** and **PD-603**, which both
contradicted the above — PD-611's reversed "Out of scope" line is struck through in place rather
than deleted, so the reversal reads as deliberate.

Also settled without a ticket: **✓ Mark refined on a Ticket is now more necessary, not less** —
approving a `refine_in_place` already auto-refines, so the button is the only route for a
hand-written ticket, which the hard gate makes the common case.
