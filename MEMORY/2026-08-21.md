## 16:30 — Turning the loop on is TWO flags, and the blocker was neither of them

`ROBOT_DISPATCH_ENABLED` was already `1`. The thing actually holding dispatch since 2026-07-30 was
the **DB** flag, `robot_state.dispatch_paused` — the env flag decides whether the loop *arms* at
boot, the DB flag whether an armed loop *dispatches*, and it is re-read every cycle.

`EVALUATOR_ENABLED=1` is the genuinely new one (PD-487 ships the Evaluator off by default).

**The pause and its reason are one field.** `setDispatchPaused(db, false)` writes NULL to
`robot_state.dispatch_paused`; a null value reads as *not paused, no reason*. There is no separate
"clear the stale reason" step — I said there was, repeatedly, having taken the phrasing from
PD-468's body without checking. Resume clears both in one write.

## 16:30 — `robot-refresh` had to deploy its own fix, and a stale shell function hid it

First `robot-refresh` after the merge rebuilt correctly but reported `buildSha: null`. Cause: the
helper is a **shell function snapshotted at login**, and the version passing `--build-arg BUILD_SHA`
only reached disk during that same run's `git pull`. `source ~/.profile` then re-run fixed it.

Worth keeping in mind whenever `pd-aliases.sh` changes: `type <fn> | grep <new-flag>` tells you
whether your shell has the current definition.

## 17:50 — Running `docker/docker-compose.yml` on the NAS takes the dashboard down

**The NAS deploy file is `docker/docker-compose.nas.yml`.** The plain `docker-compose.yml` is the
local-dev one (it has `build:`); the `.nas` one is production (`image:` from GHCR + Watchtower) and

publishes a whole block of ports for the VPN-routed stack.

I told Steve to run the dev file. It removed the working container, then failed to bind 8080, and
the dashboard was down until we found the right file. **`ls docker/` before trusting any single
compose file** — the `.nas` file even carries a comment explaining the port, which I never saw
because I `cat`-ed one file instead of listing the directory. Its path is recoverable from the
running stack: `docker inspect docker-watchtower-1 --format '{{index .Config.Labels
"com.docker.compose.project.config_files"}}'`.

Also: **compose on that NAS is v1 — `docker-compose`, hyphenated.** `docker compose` does not exist
there. And it needs `sudo` (socket permissions).

## 17:50 — A changed `.env` needs `up -d`, not `restart`

`env_file` is read when a container is **created**, so a restarted container keeps the environment
it was born with. Symptom: the app reports its config unset while the `.env` on disk is plainly
correct — here, `id-tracker` answering `configured: false` with both YouTube vars present in the
file. Cost most of the debugging time before the compose incident above.

## 17:50 — A dialog must never assert a result it did not compute

Testing turned up the widget's add-mix confirm saying *"Nothing tracked matches X"* — with **no
search behind it**. The original spec asked for one ("if typing in the name it should search inside
the existing DB for mixes with that title"); it was missed, and the confirm meant to sit on top of
it shipped alone. Steve read the sentence as confusing, which is exactly what an unearned claim
reads like.

Fixed in #333 by building the search rather than rewording the dialog. Matching is **token
containment, not substring** — "dekmantel 25" has to find "Nina Kraviz | Dekmantel Festival 2025",
which is the only duplicate case that matters and precisely the one a substring match misses.
