## Squash merges are NOT dropping commits — that was a misdiagnosis

**Correcting the record, including two earlier entries in this repo's memory.** `modal-wide` and
`enabledWhen` really were absent from `main` after #313, and I recorded it as "a squash merge
dropped a commit for the third time". Steve asked how that could happen. It can't, and it didn't:

```
15:11:24Z       commit 1 authored
15:11:50Z       commit 2 authored
15:12:59Z       PR #313 MERGED     ← 69 seconds after commit 2
Aug 11 16:47Z   commit 3 authored  ← FOUR DAYS after the merge
```

The squash took everything on the branch at merge time. **The third commit did not exist yet.** It
was then pushed to a branch whose PR was already closed, where it went nowhere — GitHub does not
merge commits into a closed PR.

The same shape explains the 08-06 note about #304/#306: #304 merged 04:22, #306 (the follow-up
fix) 04:39. That entry describes it correctly as "merged while the fix was still in flight" — a
race. A later session recast it as a squash defect, and the wrong model then compounded.

**The real hazard: Steve merges fast — 69 seconds here.** An agent that keeps committing to a
branch after its PR merges is writing into a dead branch. Before pushing more work to a branch you
already opened a PR for, check the PR is still open; if it merged, branch fresh from `main`.

The `git show origin/main:<path>` habit still earns its place — it is what caught this — but its
stated *reason* in CLAUDE.md was wrong, and a wrong mental model produces wrong fixes: the
post-merge CI guard this session nearly filed would have been solving a problem that does not
exist.

*(Unverified: the 08-06 claim that a memory file "did not survive its own PR's squash" on #297.
Same misdiagnosis is likely but was not checked.)*

## Two "no-op" buttons that were both reporting failure off-screen

Neither was dead:

- **Copy** — `navigator.clipboard` **does not exist** on `http://192.168.68.50:8088`. The async
  Clipboard API is secure-context-only, so it threw on every click. This is not a permission
  anyone can grant; it stays absent until the box is served over HTTPS. Fell back to
  `document.execCommand('copy')`. Anything else on this dashboard reaching for `navigator.clipboard`
  has the same latent bug.
- **Edit template** — it set state and rendered the editor *after the entire collapsible*, below
  three long draft bodies, so nothing scrolled into view.

Both reported their failure in a panel-level error slot far above the button that caused it. **The
lesson is placement: feedback that renders where the user is not looking is indistinguishable from
no feedback.**

## D-073 — the registry stops declaring placement

See `DECISIONS/D-073-page-membership-user-state-not-registry.md` (amends D-053). Don't re-derive it
here.

The pivot came from **Steve, not the ticket**: PD-334 asked for add/remove on top of PD-331's
`localStorage` layout, and his first answer — *"when registering widgets, they should not specify
any pages"* — turned it into a full-stack ticket that deletes `pages`, `system`, `widgetsForPage()`
and `homeWidgets()`. The body on the board was rewritten to match; the original framing is gone.

## The grill's most useful move was reading `layout.ts` before proposing anything

`loadPageLayout` dropped saved ids absent from a page's registry defaults and appended registry ids
absent from the saved array — so it was **structurally hostile to membership by design**, to make a
newly registered widget appear on pages already arranged. Naming that first is what forced the real
question (*what is the registry for?*) instead of a patch. Read the thing you're extending.

## Tests could not prove the seed guard — booting the server could

`bootstrapSchema` runs on **every** process start, so an unguarded seed would resurrect on the next
deploy every widget the user had removed. There are unit tests for it, but the convincing check was
running the server on a scratch DB, `PUT`-ing a trimmed page and an emptied one, then **restarting
the process** and re-reading. Worth the ten minutes on anything whose failure mode is "wrong after
a restart".

## A stated constraint had already expired, and I repeated it as fact

Wrote into the decision that this was "the first DB table the shell has ever owned", quoting
PROJECT.md §5. **PD-442 had landed `job_runs` in `apps/server/src/lib/` days earlier** — the
boundary was already crossed, with a worked pattern to copy. Corrected in D-073, which now records
D-053's "needs no backend" rationale as *expired* rather than overridden. Check whether a quoted
constraint is still true before treating it as one; §5 also always reserved that exact directory.

## Two repo constraints that bite and are easy to re-hit

- **`layout.ts` must not import a *value* from `widgets.ts`.** The web vitest config runs without
  the Svelte plugin, so it drags in `.svelte` files and the suite dies with a parse error pointing
  at an unrelated component. `nav-utils.ts` documents this; I hit it anyway. `resolvePlacements`
  takes the registry as a parameter — which is also why the old `loadPageLayout(pageId, defaults)`
  did. Type-only imports are fine.
- **`toast.svelte.ts` and `Toast.svelte` are the same file on macOS.** The module shadowed itself
  and the build failed with `"toast" is not exported by "src/lib/toast.svelte"` — including a line
  claiming the file imports itself. Renamed to `toast-store.svelte.ts`. Any `x.svelte.ts` rune
  module needs a name that can't collide with a component.
