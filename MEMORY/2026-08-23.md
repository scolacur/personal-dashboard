## I read a coincidence as evidence, and built a whole diagnosis on it

Steve reported seeing `db-shm` at 32 KB and `db-wal` at **0 B**. The live `-shm` is also 32 KB, so I
concluded he was looking at the archive's copy of the live DB, and wrote a confident D-029 analysis
about Hyper Backup capturing an inconsistent WAL — into the ticket.

Wrong. He was in `/volume1/docker/personal-dashboard/data/`, an orphaned July directory holding two
sidecars and **no database at all**. **32 KB is simply this database's shm size** — it identifies
nothing. A value that matches in every candidate location cannot discriminate between them, and I
used it as though it could.

**Before treating a matching value as identification, ask whether it would differ between the
candidates.** The discriminating field was sitting right there and I never looked at it: the live
WAL is 4 MB, the thing he described was 0 B. That one number ruled out the interpretation I chose.

Corrected in PD-553 rather than left for tomorrow-Steve to act on.

## Three lookalike directories, only one of them real

```
/volume1/docker/personal-dashboard/
├── backups/                      ← DECOY: retired Sortie .quota-refund.bak files (D-055)
├── data/                         ← DECOY: orphaned griller dir, Jul 6, sidecars with no DB
└── personal-dashboard/           ← the repo checkout — the name repeats
    └── data/
        ├── dashboard.db          ← live (+ its real 4 MB -wal)
        └── backups/              ← the snapshots
```

The doubled directory name is why `data/backups` looked absent in Backup Explorer. Both decoys are
worth deleting **after** a restore is proven — a directory named `data` containing a 0-byte WAL and
no database is precisely what misleads during an outage.

**The related hazard, written into the restore procedure:** when swapping a restored file into
`data/dashboard.db`, delete any stale `-wal`/`-shm` beside it first. SQLite will apply an orphaned
WAL to a fresh database. Same failure as the decoy directory, in the one moment it costs the most.

## Where recovery information can and cannot live

The Hyper Backup archive is encrypted (`enable_data_encrypt=true`) and the key had already been
exported to Steve's cloud storage — off the NAS, which is the property that matters.

Two constraints surfaced when he asked to write the location down, and both generalise:

- **This repo is public.** A location for an off-site decryption key cannot go in `MEMORY/`, a
  runbook, or any tracked file — that publishes it permanently, in git history. It went on the
  board instead (LAN-only, unindexed). *The exact path is deliberately not recorded here.*
- **But the board cannot be its home either, for the same reason the key could not live on the
  NAS.** The board runs *on* the NAS. In the disaster the key exists for, the pointer dies with the
  machine. It is useful for "I forget where I put it" and useless for the real case. The durable
  copy belongs in a password manager.
