**PD-693 ([Epic] Import the 2025 Daily Log and correlate it)**, P4, four members: PD-694 (import into
a shared store) → PD-695 (derived columns) → PD-696 (the correlations) → PD-697 (visualise).

**The storage question resolved, and the interesting part is that it was never a conflict.** Steve
chose a **shared daily-log table several widgets read**, framing it as relaxing PROJECT.md §5's
no-cross-widget-imports rule and guessing the rule's purpose was "avoiding spaghetti code". **It is
not a relaxation.** §5 forbids *widget-to-widget imports* — widget A reaching into widget B's folder —
and in the same sentence routes shared things to `packages/shared` (types) or `apps/server/src/lib/`
(server-side infrastructure), which is exactly where PD-442 put the shared `job_runs` store. A shared
daily-log store in `lib/` is the **documented pattern**, not an exception to it.

Two things genuinely do change, both on the Epic: this is the **first shared *domain* table**
(`job_runs` was infrastructure), so it **owes a `D-NNN`**; and §9's Firewall entry applies — a shared
access layer is **middleware, not a firewall**, since any widget can open its own `better-sqlite3`
handle. It must not get described as a boundary later.

The three statistical caveats survived from the original draft and are on the Epic: ~two dozen
predictors against Mood means **one in twenty looks significant by chance**, so decide in advance how
a finding earns belief; **correlation gives no direction** (the previous-day and rolling-window
framings are already a partial fix); and **variable types decide the coefficient** — Spearman is the
safer default for ordinal data. PD-695 carries the rule that matters mechanically: **lag and window by
date, never by row position**, or every gap in the log silently corrupts the rows after it.

**939** instrumented `.ts` lines in `apps/web`. Component code is ~5.5× what web currently measures,
and **zero component tests exist**. So instrumenting `.svelte` under the existing `coverage.all: true`
convention moves the repo-wide denominator from ~5,200 to ~10,300 with the numerator unchanged:
**~72% → ~36-40%**.

That is the honest number PD-484 asks for, but it **breaks the ticket's own plan** — "set a floor at
the measured baseline and ratchet upward" gives a 36% floor that cannot ratchet, because writing
component tests is explicitly *out of scope* on the same ticket. **Recommended split: a `.ts` floor
that gates, and a `.svelte` number that reports only**, until tests exist to raise it.

**What makes instrumentation cheaper than feared**, all measured: the web app is fully runes-based
(60 components use `$props()`, 47 `$state()`, **0** legacy `export let`), only **6 of 106** import
`$app/*`, and **none** import `$env/*`. 54 import `$lib/*`, which is one `resolve.alias`. The genuine
unknown is v8-provider source-map attribution back through the Svelte 5 compiler; the fallback is the
istanbul provider via `vite-plugin-istanbul`.
