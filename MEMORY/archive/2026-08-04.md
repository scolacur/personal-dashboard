### RESOLVED — an orphaned OS-update APFS snapshot was pinning everything

**Root cause:** a single non-purgeable snapshot on `disk3s5`,
`com.apple.os.update-3379F3DC…` (uuid `08A15798-9E71-481C-BD83-0637E42A4CDB`), flagged
*"This snapshot limits the minimum size of APFS Container disk3"*. macOS takes one as a rollback
point before staging a system update. Every block deleted after it was taken stayed pinned — which
is why deleting 130 GB (`~/Music/Video Assets…` 116 GB + `~/Downloads` 23→8.6 GB) and emptying the
Trash **twice** freed exactly nothing.

**It was self-sustaining.** `/var/log/install.log` showed `softwareupdated` still retrying *that
morning* (01:31, Ventura 13.7.8 → macOS 26.6 offered, "pending follow ups count=1"). A major
upgrade needs ~20 GB to stage; the disk had ~200 MB; the attempt failed without cleaning up the
snapshot and re-queued. Loop: snapshot pins blocks → disk full → update can't finish → snapshot
survives → repeat.

**Fix** (Steve ran it): `sudo diskutil apfs deleteSnapshot disk3s5 -uuid <uuid>` →
**226 MiB → 420 GiB free**, volume 100% → 78%.

**Diagnostic order that would have found this in one step:** `diskutil apfs listSnapshots
/System/Volumes/Data` — *not* `tmutil listlocalsnapshots /`, which lists the names but does not
show which volume a snapshot pins or that it is non-purgeable. I checked `tmutil` early, saw only
`com.apple.os.update-*` entries, and wrongly dismissed them as negligible. **If deletions don't
free space, check for snapshots first — before Trash, before open file handles.**

**Follow-up owed:** the pending update is still queued. Either install it now that there's room, or
pause it — left alone on a tight disk it can take a fresh snapshot and restart the whole cycle.

## Established for PD-457: audit runs do not stack

Verified in code, not assumed: `audit-cron.ts` holds **no reference to any prior run**, and findings
are stored scoped to a `run_id` (`listFindings(db, runId)`). So each run is an **independent full
sweep** — findings never accumulate into one growing list, and the report page shows one run.

But the corollary is the part that bites, and it's what the info text must say: **an unresolved
issue is re-raised as a brand-new finding every run.** Combined with `decision` having no write path
(the 07-30 finding — `audit-store.ts` exposes only `listRuns`/`getRun`/`listFindings`), a finding
you consciously *rejected* is indistinguishable from one you never saw. PD-287 is the fix.

## PD-294 — the storage representation nearly made it a no-op

`agent_tickets.priority` is `TEXT NOT NULL DEFAULT 'none'` — **unset is the sentinel string
`'none'`, never SQL NULL**, and the store maps `'none' ↔ null` only at the API boundary. My first
version tested `priority IS NULL`, which would have been dead code against **150 of 480** live
tickets. Caught by reading `schema.ts` rather than trusting the API response I'd been reading all
session. **When writing SQL against this DB, check the column, not the JSON.**

The `CASE` is kept even though `'none' > 'P5'` holds under BINARY collation — that's an ASCII
accident, not a contract.

## PD-437 — the sheet was not a table, and the ticket's spec was wrong

The importer as specified rejected **all 46 rows** of Steve's real export. The sheet's actual shape:
column 1 is free prose (sale terms, then a `WTTF:` marker, then a want-list); column 2 "Type" is a
**section marker applying downward** (`MODULES` / `MISC` / `Feelers` / `Probably won't sell`), not
WTB/WTS/WTT. One row can carry a terms line, a section change *and* a listing at once.

That the import failed **loudly, with per-row reasons**, is what made this diagnosable in one run —
the "skip and report, never guess" rule earned its keep immediately.

Decisions Steve made on the rebuild:

- **Taxonomy invented rather than mirroring the sheet**: `sale_status` (`for-sale` / `feelers` /

- **`WTT` means "want to trade FOR"** — the WTTF list is gear he'd *accept*, not gear he offers.
  `isSellable` is WTS-only. I had this wrong initially; left alone, PD-439 would have drafted his
  want-list into the for-sale table.
- Want-list imports as WTT rows; terms are **offered, never applied** (a re-import must not clobber
  terms edited in-app).

Two data traps worth remembering: the header is `Current Location (For my personal reference)`, so
header matching **strips trailing parentheticals** or the column silently imports empty; and the
