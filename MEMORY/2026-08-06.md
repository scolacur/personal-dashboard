## CI silently not running means your PR conflicts

Three events on PR #293 fired `path-guard` but never `ci`. Not a flake: the PR **conflicted with
main**, so GitHub could not build `refs/pull/N/merge` — and `pull_request`-triggered workflows do not
queue at all, while `pull_request_target` ones (path-guard) still run. **path-guard running alone is
the tell for a conflicting PR.**

## 01:24 — D-067 shipped: the path-guard is author-scoped (#295)

The ack is now required from every author except `AUTHORS_EXEMPT` (just `scolacur`), and never
skipped on a `robot/*` / `sortie/*` head branch whoever opened the PR. The denylist is unchanged —
this scopes *who* is gated, not *what* is sensitive. Rationale, alternatives and the fail-closed
argument are in `DECISIONS.md` **D-067** (amends D-047); don't re-derive them here.

Two implementation details that are easy to get wrong on a *required* check, both load-bearing:

- **Exemption is a green exit inside the step, not a job-level `if:`.** A skipped job reports a
  `skipped` conclusion, which is not the success branch protection expects.
- **The `robot/*` branch test is a backstop, not redundancy.** If the Robot's identity ever
  collapses onto Steve's PAT, author-matching alone would exempt every Robot PR *and keep reporting
  green*. The prefix check makes that failure loud.

## 00:50 — "Firewall" is now a pinned glossary term, and the DB layer is not one

PD-474's direction D was written up as a DB access layer / "firewall". It is **middleware** — a
widget can always open its own `better-sqlite3` handle, so the caller can decline to use it. The
only firewall in this system is the Robot's DB-blind uid (D-055), where a *uid* makes the boundary
unavoidable from outside the code. Renamed throughout PD-474 and added to PROJECT.md §9 with the
test to apply to any proposed control: **can the caller decline to use it?** If yes, it is
middleware, and calling it a firewall makes a later reader trust it for something it cannot do.
