## The ID Tracker cue write returns `{cue, warnings}`, not a Cue

`POST /api/widgets/id-tracker/mixes/:id/cues` returns `CueWrite` — `{ cue, warnings }`. My printer
read `res['id']`, threw `KeyError`, and reported **FAIL** for all six cues that had in fact been
written correctly (ids 13–18). The `warnings` half is the point: `validatePosition` can accept a cue

## The wrap-up nearly destroyed three other sessions' memory

The whole memory side of this session was done in the **stale main tree**, and `git status` looked
completely reasonable right up to the moment of committing. What was staged would have:

- **Deleted six real `MEMORY.md` index lines.** The stale local index had four day lines;
  `origin/main` had seven, including 08-07 and 08-21 that this tree had never seen. Rewriting the
  index from a stale copy is a delete, not an edit — and `MEMORY.md` is the always-loaded file, so
  the loss would have been invisible until someone went looking for a day that no longer resolved.
- **Overwritten `MEMORY/2026-08-12.md`.** An untracked local file of that name held one session's
  notes (PD-383 → D-076); the upstream file of the *same name* holds **two different** 08-12
  sessions (D-074/BST and PD-334/D-073). Untracked meant "never committed", which read as "safe to
  add" — it was in fact a name collision with other people's work.
- **Re-run an aging pass that was already partly wrong**, having been computed against an index
  missing 08-07.

The catch was checking `git log HEAD..origin/main -- MEMORY/` *before* committing rather than after.
**Generalise it: any wrap-up that rewrites a shared index file must diff that file against
`origin/main` first**, because the destructive case looks identical to the correct one in
`git status` — both are "M MEMORY.md".

Redone properly in a worktree off `origin/main` (rule 1) — five day files archived (07-30 through
**08-07**), the 08-12 session appended as a third section rather than replacing the file, and one
new index line. No code touched, so `npm run verify` was not run and `npm ci` was skipped; CI runs
it on the PR.

## The backup job was running, and had silently stopped for five nights

Question asked: is the nightly DB backup running and producing full backups? Answer: **yes on both
counts, and it had already failed once with nobody the wiser.**

What verified clean — snapshots at 08-13, 08-19 and 08-22 all pass `integrity_check`, are
`journal_mode=delete` with no `-wal`/`-shm` sidecars riding along, carry every table the live DB had
at that moment, and hold row counts consistent with their timestamp (the 08-22 snapshot has
`music_tracker_tracks = 33`, exactly the count before that day's entry work). Retention is correct:
oldest is 08-08, 14 days back.

**What did not: there are no snapshots for 08-14 → 08-18.** Five consecutive nights. Not retention —
those are newer than the cutoff. Board activity has a hole in precisely the same window, so the app
was almost certainly down. That could not be confirmed: `sudo` on the NAS wants a password, so
container logs are unreachable from an agent session. **The only evidence of a five-day outage was a
gap in a directory listing**, found six weeks later by hand.

## `PRAGMA integrity_check` returns `ok` for an empty database

This is the finding worth carrying forward. The job's sole verification was `integrity_check`, which
is a *structural* check — an empty or schema-only file passes it. So a run that silently captured
nothing would have been written, verified, logged a success, and then used to **prune the previous
fourteen days of good snapshots**, surfacing only at a restore.

Not hypothetical: `data/dashboard.db.bak.1782919239` is on the NAS at **4096 bytes** — a valid,
empty SQLite file of exactly that shape.

**Steve's instinct was "check it's the same size as the DB"; that specific check cannot work**, and
the reason is worth keeping: the snapshot is checkpointed into one file while the live DB carries a
separate `-wal` (4.1 MB against a 1.8 MB main file at the time). The two differ in *both* directions,
so equality would fire nightly and get muted. Shipped instead, in **PD-550 / PR #350** (merged,
`d63fb2e`):

- **schema parity** — every source table present in the snapshot;
- **row-count floor**, 5% band — the real check. Not equality either: `.backup()` is point-in-time
  while the app keeps writing, so the source is legitimately *ahead* by the time both are counted;
- **size floor**, 50% — coarse, only catches the stub.

Also wired the job into `job_runs` under `DB_BACKUP_JOB`. It had been **the only scheduled job with
no run history at all**, which is why the outage was invisible: the sole evidence it ever ran was
the files themselves.

**Proven live end-to-end.** Merge → `deploy.yml` → GHCR → Watchtower, then the 03:00 UTC run
executed through the new path: `{"targets":1,"verified":1,"failed":0,"tables":34,"rows":2828,`
`"bytes":1912832,"pruned":1}` — `bytes` matching the file on disk exactly, and the prune happening
only after the new snapshot verified.

Filed **PD-552** (alert when a scheduled job stops running). Its framing matters more than its
scope: **an in-process check cannot fire while the process is down** — it can only report the gap on
recovery. A real dead-man's switch has to live off-box, and is scoped out. Two knots flagged in the
ticket: the cron schedules are declared twice (web registry for display, server for the real
registration), and `createNotification` lives inside the task-monitor widget while `db-backup` is
core, which PROJECT.md §5 forbids importing across.
