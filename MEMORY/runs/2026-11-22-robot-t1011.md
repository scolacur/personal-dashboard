# [Refine] Auto-start picks by priority: one list, new tickets win only within a priority, Epics before members

**What shipped:** Collapsed the refine auto-start's two-list fallback (`nextAutostartCandidate` ?? `nextBackfillCandidate`) in `apps/agent-worker/src/jobs/refine/autostart.ts` into one eligibility set ordered by priority → new-before-old within a priority → oldest. The PD-748 Epic gate, the `refine_backfill_excluded` switch, and the no-prior-thread rule now apply to every candidate (new tickets included), not just the old backfill ones. The "new" boundary (`since`) is now only a tie-breaker. Kept the published `RefineAutostartStatus` shape (`queued` = new eligible, `backfillRemaining` = old eligible), so no server/web consumer change was needed.

**Worth remembering:**
- The web never consumes `refineAutostart.queued`/`backfillRemaining` (only the server route exposes it in system status), so keeping the status shape split was zero-risk and avoided touching shared types.
- Only one existing test asserted the old new-first-regardless-of-priority order ("drips older tickets..."); it was renamed/updated. The other backfill/Epic tests passed unchanged because the unified `ELIGIBLE_WHERE` is a strict superset of both old WHERE clauses minus the `created_at` split.
- `apps/server/src/backup.spec.ts` ("survives an unreachable one") intermittently TIMES OUT at the default 5s in this sandbox — it actually runs in ~5.6s (passes at `--testTimeout=60000`). It's a slow-environment flake, unrelated to this change (apps/server untouched); a less-loaded verify run passes it.
