## The session-start memory aging pass made wrong writes against a stale tree

`/harness` archives day files *before* reading the index, and it did so against a checkout 20
commits behind — one missing `2026-08-07`, `2026-08-21` and `MEMORY/runs/` entirely. Reverted
cleanly. **The aging pass is the one `/harness` step where a stale checkout does not merely mislead,
it mutates.** `git fetch` belongs before it, not after.

## D-078 was wrong about the maintenance hold, and the code said so

D-078 specified "a third `kind` on the existing hold, not new machinery". But `session_limit_until`
is a **single k/v slot, last-writer-wins**. Sharing it fails silently both ways, and the bad
direction is: the cycle finishes, releases "the hold", and nulls a session-limit hold that arrived
while it ran — resuming dispatch into a spent quota, which is the exact PD-470 bug. Two conditions
with independent lifetimes need two slots. See `D-TMP-PD498a`.

**The general shape: a decision written at design time can be wrong about code it did not read.**
Check the mechanism a decision assumes before implementing it as written.

## Steve inverted the architecture, and it was the right call

Mid-session he asked for a Dev Ops Jobs page section. It turned out to be an inversion, not a layout
change: the **hold** becomes the scheduled thing and jobs subscribe to it, rather than consolidation
scheduling itself and taking a hold internally. See `D-TMP-PD498b`.

The argument that settled it is worth keeping: **the risky machinery was never the work, it was the
window** — draining, holding, bounding, releasing on every exit path. And "Run now" has no safe
meaning outside a window, so the window has to be a thing you can open and be inside.

## Five live runs, each failing further along — and the tests could not have caught any of them

1. **Drain would never reach zero.** `inFlightRunCount` counted a `running` row from 2026-07-16
   whose ticket had been `completed` for five weeks. The stall reconciler only reaches runs whose
   ticket is `working`, so that row is permanent. Every cycle would have burned its 2h timeout
   forever. Found by *reading production state*, not by a test — every test injects that count.
2. **No git identity.** Container runs as root. Commit failed after the rename had been applied.
3. **The failure left the checkout dirty on a `numbering/` branch** — 36 staged changes. That is the
   PD-340 failure mode from a new direction: the grounding checkout is shared, `pullLatest` refreshes
   it, every job grounds against it. Restoration now runs on every exit path.
4. **`GH_TOKEN` does not authenticate `git push`.** Auth has to travel as `-c http.extraHeader`, as
   `shared/checkout.ts` already does. **And that introduces a leak**: `execFile`'s error embeds the
   whole argv, so a failed push would have written the write token into `job_runs.error`, which the
   API serves and the page renders. Redaction is not optional once auth is an argument.
5. **`gh pr checks` says "no checks reported" in the first seconds after a PR opens.** That is
   "too early", not "failed".

**The pattern across all five: every one lived in the seam between the code and its environment** —
a container's identity, a shared checkout, a token's scope, GitHub's timing, a five-week-old DB row.
Unit tests with injected boundaries cannot reach any of that. The live run is not a formality.

## A test that passed by no longer testing anything

The "propagates a failure" spec threw on `args[0] === 'push'`. Adding auth args made push start with
`-c`, so the condition stopped matching, nothing threw, and the cycle "succeeded" — green, and
meaningless. It only surfaced because an unrelated change made it fail loudly. **A test that matches
on argument position is one refactor away from silently testing nothing.**

## The dangling-citation check is unactionable, and was knowable in advance

It reported 100% false positives on the first run — every id was a doc example or test fixture
(`D-TMP-PD513a` ×18, `D-TMP-PD999z` ×8, …), none real. `D-TMP-PD498a` now carries an amendment
saying so; **PD-548** decides between a reserved example namespace and dropping it.

**The transferable lesson:** "report it and let a human look" is only a real answer when the report
can distinguish its subject from ordinary background. One `git grep` before shipping would have
shown it could not.

## Path-guard: the exemption is weaker than the proof (PD-547)

A consolidation PR rewrites citations wherever they live, including sensitive paths (it hit
`task-monitor/schema.ts`). The bot is not `AUTHORS_EXEMPT`, so path-guard reds every cycle. #348
gates the merge on `verify` alone, per D-078 — but that is a standing exemption based on *who*
opened the PR, and a rewriter bug would sail through it.

Steve's better framing, sharpened twice: prove the diff **is** a rename. Not "comments only" (fuzzy
across string literals and markdown), and not just "mapping(removed) == added" — that constrains
modified pairs only, so a pure **addition** has no counterpart and slips through. The conjunction:
every removed line contains `D-TMP-`; every added line is `mapping(removed)`, paired in order; the
only exceptions the `DECISIONS/` renames and the generated index, which is validated by
regenerating. That is PD-547.

An "equal line counts per file" rule was drafted and dropped: redundant (1:1 pairing already catches
an unpaired addition) and fragile (`D-TMP-PD383a` is longer than `D-080`, so a reflow would fail a
legitimate rename). **A check that cries wolf on correct input gets bypassed** — which is how the
guard it replaces got into trouble in the first place.
