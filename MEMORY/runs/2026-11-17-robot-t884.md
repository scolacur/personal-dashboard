# [Habit Tracker] Schedules (days-of-week, N-per-week, effective-dated), streaks and extras

**What shipped:** PD-722 — `habit_schedules` (effective-dated rows), pure `isDue` / `perWeekProgress` /
`streak` / `scheduleForDay` logic in `@dashboard/shared`, a server-computed `GET /api/habits/today`
view (due + per-week progress + current/longest streak per active item), a `PUT /items/:id/schedule`
route, and the Today/Habits UI (🔥N badges, "✓ 3/3 this week", a schedule editor modal). D-095.

**Worth remembering:**
- Pattern precedent: the shared package has **no test runner**; pure shared functions are unit-tested
  from `apps/server/src/lib/*.spec.ts` (that's how `habitDay` was tested). I followed that — the
  schedule/streak unit tests live in `apps/server/src/lib/habits-schedule.spec.ts`, not in shared.
- Streak history is judged **per-period by the schedule in force then** (effective-dated), so a
  schedule change never rewrites the past. That's the whole reason the Today view is server-computed:
  `longest` needs full completion history, which the client doesn't hold.
- Weekday mask is **Monday-indexed** (bit0=Mon..bit6=Sun) to match the Mon–Sun habit week.
- `backup.spec.ts` flakes with a 5s per-test timeout under full-suite load (passes in isolation at
  ~5.08s). Unrelated to this ticket — a second verify run was green.
- One benign svelte warning (`state_referenced_locally`) in ScheduleEditor: the editor deliberately
  seeds `$state` once from the `schedule` prop. Non-blocking; the repo already tolerates such warnings.
