# [Robot] Queue rule: each Robot subtype runs at most one at a time (per-subtype concurrency cap of 1)

**What shipped:** A per-code-area concurrency cap (PD-951) in the Robot loop's dispatch selection
(`apps/agent-worker/src/jobs/robot/select.ts`). `RobotCandidate` now carries its `effectiveCoderArea`
(resolved in `robotQueueCandidates` SQL from the ticket's `coder_area`, then its Epic's, then
`general`). `selectDispatchable` skips a candidate whose area already has a running Coder — from a
prior cycle (`runningCoderAreas` reads `agent_runs` status='running') or claimed earlier in the same
cycle — while the global `ROBOT_CONCURRENCY` still bounds the total. The per-area cap is a named
constant `PER_AREA_CONCURRENCY = 1`, not a config knob (per the ticket). `areaBusySkips` names the
held-back tickets with reason "waiting: area <x> busy"; the loop logs them beside the existing
`queuedBlockedByAgentState` / `queuedButUnrefined` skip reporters.

**Worth remembering:**
- Runs are currently awaited sequentially *within* one poll cycle, and `selectDispatchable` is
  called once with `inFlight=0`, so today the cap mostly bites *within a cycle* (two same-area
  candidates → one selected). `runningCoderAreas` (reading `agent_runs`) is the part that makes it
  correct once `ROBOT_CONCURRENCY > 1` lets runs outlive a cycle (PD-512). Both paths are tested.
- Deliberate distinction: `areaBusySkips` reports ONLY candidates held back *because their area is
  full*, not ones merely over the global concurrency cap (those wait on capacity, a different
  reason). `planDispatch` is the single pass both `selectDispatchable` and `areaBusySkips` derive
  from, so the two can never disagree.
- Test fallout worth noting: because `general` is capped like any other area, the existing
  multi-ticket concurrency/breaker/budget tests in `robot.spec.ts` (which dispatch ids 1,2,3 in one
  cycle) would have collapsed to one dispatch. Fixed by giving `addQueued` a DISTINCT default area
  per id (`CODER_AREA_IDS[id % len]`), and the `select.spec.ts` `cand` helper the same — so those
  tests still exercise concurrency, with the area dimension set so it doesn't interfere. Not a
  weakening: the new same-area single-dispatch behaviour is covered by dedicated PD-951 tests.
- `RobotCandidate` gained a required field, so every literal had to grow `coderArea` (two in
  `robot.spec.ts`, one in `session.spec.ts`). `runningCoderAreas` is try/catch → empty map so a
  cold boot before `agent_runs` exists doesn't throw.
