# [Robot] agent-worker deploy-drain CLI + release the deploy hold on startup

**What shipped:** A new esbuild entry point `apps/agent-worker/src/deploy-drain.ts` (→ `dist/deploy-drain.js`)
that a Watchtower pre-update hook runs: it takes a **deploy hold** (bounded by `stallThresholdMs`) so no new
Robot run dispatches, then exits **75** (EX_TEMPFAIL) if a run is in flight or **0** if none. The deploy hold is
a dedicated `robot_state` slot (`deploy_hold`) with its own take/release/active functions in `robot/state.ts`,
wired into the Robot dispatch gate (`robot.ts`). On worker boot, `index.ts` calls
`releaseDeployHoldOnStartup` so dispatch resumes after the recreate. Design recorded in D-105.

**Worth remembering:**
- The ticket Context said to *reuse* `takeMaintenanceHold`/etc, but the Task section offered a choice.
  I went with a **dedicated slot** (not a `reason` on the maintenance hold) because `state.ts` already
  documents at length why two conditions with independent lifetimes must not share one last-writer-wins
  `robot_state` slot — sharing reintroduces a silent clobber both ways (deploy drain overwrites a manual
  maintenance window; boot-release nulls one). See D-105.
- `inFlightRunCount` only counts a `running` run whose ticket is still `working`, so a stale `running` row
  (a real production artifact — see `in-flight.ts` note) can never block a deploy forever. Tested that path.
- Entry-point guard is `if (require.main === module)` (CJS build), mirroring `capture-cli.ts`, so the spec can
  import `runDeployDrain`/`releaseDeployHoldOnStartup` without triggering `main()`.
- Exit 75 confirmed from Watchtower lifecycle-hook semantics (EX_TEMPFAIL = cancel + retry next poll, no error
  log). Did not fetch Watchtower docs (host not on the allowlist); relied on documented sysexits semantics.
- `apps/agent-worker/**` is a sensitive path now (D-103), so this `robot/*` PR needs `sensitive-change-approved`.
