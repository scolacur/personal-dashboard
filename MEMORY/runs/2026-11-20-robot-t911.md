# [Board] A body edit to a refined ticket must say whether it stays refined — UI prompt + API 409 (D-097)

**What shipped:** A body-changing `PATCH` on a refined ticket now must carry an explicit `refined`
(409 `REFINED_CHOICE_REQUIRED` otherwise); keep → stays refined + `refine_kept`, clear → unrefined +
`refine_invalidated{cause:'body'}`, and clearing on an Epic reuses the membership-invalidation path
(stale + un-arm). The board edit modal and the detail page route body edits through a shared
`resolveUnrefineChoice` helper that prompts "Mark this unrefined?" (default Yes).

**Worth remembering:**
- The 409 guard lives at the **route layer** (`refinedChoiceGuardFailure` in `ticket-guards.ts`),
  not in `updateTicket`, for the exact PD-542 reason: `approveRefine`/Populate call `updateTicket`
  internally and already state `refined` explicitly, so they must not be refused. `updateTicket`
  only carries the *behaviour* (logging + Epic invalidation), keyed on
  `existing.refined && bodyChanged && patch.refined !== undefined`.
- `invalidateEpicRefinement` gained a `cause` param (default `'members'`); the body path passes
  `'body'`. It MUST run before the main UPDATE writes `refined=0`, or it early-returns as
  already-clear — so the epic-body-clear call is placed first inside the transaction.
- Passing `refined:false` explicitly still clears the flag even on a byte-identical body (the
  generic field is honoured); the byte-comparison only governs the *prompt/409 requirement* and the
  `cause:'body'` logging. The real "unchanged body" case omits `refined` entirely.
- The detail page has **no** body-edit control yet (that's PD-396, out of scope), so its
  `updateField` wiring is forward-compatible: it prompts if/when a body is ever passed. Only the
  board's `TicketFormModal` edits a body today.
