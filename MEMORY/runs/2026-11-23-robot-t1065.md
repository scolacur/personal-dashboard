# [bugfix] [Evaluator] A ticket range in a PR title (PD-859–PD-862) links only its endpoints

**What shipped:** `linkedTickets` (`apps/agent-worker/src/jobs/evaluate/all-prs.ts`) now expands a
same-prefix ticket range in the branch or title (`PD-859–PD-862`, `-`, `..`, " to "; en/em dash)
into every id in it before the per-id match, so a range PR is judged against all its tickets
instead of just the two endpoints reading the middle as scope creep (PD-903). New `expandRanges`
helper, capped at `MAX_RANGE_IDS=20` (over-cap falls back to endpoints + a warn); mixed-prefix
pairs (`PD-5–C-9`) and non-existent middle ids are left/dropped by the existing lookup.

**Worth remembering:**
- The ticket's Notes said expand "in the branch or title". The branch's leading-id extraction is
  deliberately anchored (`^[a-z]{1,4}-\d+(?:-|$)`) so a slug like `fix-123` is NOT read as a ref —
  I added a separate anchored branch-range regex rather than running the broad `DISPLAY_ID` over the
  whole branch, which would have introduced `word-number` false positives.
- `npm run verify` was RED on clean main in this sandbox: two PD-884 security-lens tests
  (`a second security error…`, `re-runs ONLY the errored security lens…`) failed because the
  `lensDeps` helper omitted the `readStatus` stub that the sibling `deps` helper has, so the gate's
  "already Steve-approved?" check shelled out to real `gh` and errored where `gh` is unauthenticated,
  leaving the status unposted. In CI `gh api` returns `null` and they pass. I added the same
  `readStatus: {ok:true,current:null}` stub to `lensDeps` to make them hermetic — no assertion
  weakened. (The `no such table: agent_projects` log from `adoptableTicket` is caught and harmless.)
