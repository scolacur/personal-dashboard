# [Audit] Adversarial verify stage + run token/cost metadata

**What shipped:** PD-839 (slice 2/3 of PD-284). The Ticket Audit now runs a single pooled
adversarial verify turn after the per-project fan-out: it reviews every non-`keep` candidate
against its cited evidence and DROPs the indefensible ones or DOWNGRADEs their confidence,
persisting survivors only. Also captures per-turn `usage` + `total_cost_usd`, sums it across the
fan-out + verify turns, and writes new `audit_run` columns (`input_tokens`/`output_tokens`/
`total_tokens`/`cost_usd`). See D-122.

**Worth remembering:**
- Persistence had to move OUT of `auditOneProject` and to the end of `runAuditPass`: the verify
  stage is pooled across all projects, so findings can't be written inline anymore. `auditOneProject`
  now returns in-memory `PendingFinding`s; the run persists survivors last. Reconciliation (PD-285)
  still computes decisions per-project pre-verify — dropping a finding doesn't affect others'
  decisions because they key independently on `(ticket_id, type)`.
- Verify reuses the SAME injectable runner as the fan-out (`deps.runVerify ?? deps.runAgent`), with a
  different system prompt. This matters for the existing tests: a test that stubs `runAgent` and emits
  a non-`keep` finding will now ALSO drive the verify turn with that stub. Unrecognised verify output
  (no `index`/`verdict`) safely upholds everything, so most existing tests pass untouched — the one
  exception was the `single:CORE` test that counts fan-out prompts, which needed a `runVerify` stub
  to keep its count at 1.
- Verify fails OPEN: a thrown error or `ok:false` keeps all candidates. It's a precision filter on an
  advisory signal; losing the fan-out's output to a second-agent hiccup is worse than an occasional
  un-dropped finding.
- The cost columns follow PD-910's pattern exactly: written by a separate column-guarded statement
  (`recordAuditRunCost`) so a worker ahead of the server migration still closes the run. `finishRun`
  calls it when `usage` is passed. `AuditRun` (+ the server `rowToRun`) gained the four nullable fields.
- Schema change (sensitive path): `apps/server/.../schema.ts` migrate step — the PR needs the
  `sensitive-change-approved` label (path-guard Tier 1).
