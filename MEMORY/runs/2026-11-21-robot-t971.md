# [Auto-queue] Detail page: queue-eligibility checklist on every ticket and Epic

**What shipped:** A shared `QueueEligibilityChecklist.svelte` (+ pure `queue-eligibility-view.ts`
view model) rendered below Details on every ticket/Epic detail page (D-103, PD-809). It shows the
verdict line, a muted AUTO_QUEUE off/dry-run note, the flat ✓/✗ criteria + capacity rows, and — on
an Epic — the Epic-level criteria plus a member roll-up with per-member verdicts and links.

**Worth remembering:**
- The eligibility API (PD-808) was already on `main`; I extended the shared layer rather than
  re-deriving: added `AutoQueueMode` + `parseAutoQueueMode` (reads `process.env.AUTO_QUEUE`, defaults
  `off`) and `mode` on `AutoQueueEligibilityResponse`; added an optional `remedy` to
  `AutoQueueCriterion` carried through from `queueBlockers` so the checklist can link a reason to the
  Epic or the blocker; and pure wording helpers (`autoQueueVerdictLine`, `autoQueueEpicVerdictLine`,
  `autoQueueModeNote`, `autoQueueMemberRollup`, `AUTO_QUEUE_VERDICT_SHORT`).
- apps/web has **no DOM test runner**, so all verdict/row derivation lives in the pure
  `queue-eligibility-view.ts` and is tested there (17 cases); the component only paints it. Shared
  wording helpers are tested from `apps/server` beside the predicate (packages/shared has no runner).
- Capacity rows render only for `eligible`/`not-eligible` member verdicts (moot for in-queue,
  terminal, human-work); always for an Epic. The `worker-healthy` limb shows no `current / limit`.
- Visual fixture: to get an **eligible** ticket to photograph, the task-tracker fixture needed an
  ACTIVE (queued) Epic whose only member is a refined, Ready, robot ticket still in Backlog. Order
  matters: queue the Epic while EMPTY, then add the member (a ticket created into a queued Epic stays
  Backlog, D-080), then re-mark the Epic refined (adding a member re-stales it, D-089).
