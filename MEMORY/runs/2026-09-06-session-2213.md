## 22:25 — The `.svelte` gap is the whole cost, and it is bigger than the ticket implies

Measured, not estimated: **5,127 non-blank `<script>` lines across 106 components** (95 have a
script block), against **939** instrumented `.ts` lines in `apps/web` today. Component code is
~5.5× the volume of what web currently measures, and **zero component tests exist**.

So instrumenting `.svelte` under the existing `coverage.all: true` convention moves the repo-wide
denominator from ~5,200 to ~10,300 lines with the numerator unchanged: **~72% → ~36-40%**.
That is the honest number PD-484 asks for, but it breaks the ticket's own plan — "set a floor at
the measured baseline and ratchet upward" gives a 36% floor that cannot ratchet, because writing
component tests is explicitly *out of scope* on the same ticket. **Recommended split: a `.ts`
floor that gates, and a `.svelte` number that reports only** until tests exist to raise it.

**What makes the instrumentation cheaper than feared**, all measured: the web app is fully
**runes-based** (60 components use `$props()`, 47 use `$state()`, **0** use legacy `export let`),
only **6 of 106** components import `$app/*` (3 `$app/state`, 2 `$app/stores`, 1 each
`$app/navigation` / `$app/environment`), and **none** import `$env/*`. 54 import `$lib/*`, which
is one `resolve.alias`. The genuine unknown is v8-provider source-map attribution back through
the Svelte 5 compiler; the fallback is the istanbul provider via `vite-plugin-istanbul`.
