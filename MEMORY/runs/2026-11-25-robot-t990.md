# [Audit] Relations as truth: read existing + emit LINK/UNLINK/duplicate findings (advisory)

**What shipped:** The Ticket Audit now reads each audited ticket's existing relations (new
`getRelationsForTickets` SQL in `audit-db.ts`, mirroring the server store's `listRelations`),
injects them into the per-ticket prompt as truth, and can emit `link`/`unlink`/`duplicate`
findings. Two nullable columns (`target_ticket_id`, `relation_type`) were added to `audit_finding`
(CREATE + migrate), threaded through `FindingInput`/`insertFinding`, the shared `AuditFinding`
interface, and the server `rowToFinding`. Still fully advisory/read-only — no relation is written
(that's Child B / PD-287).

**Worth remembering:**
- Backticks inside a SQL comment break the `db.exec(\`...\`)` template literal — esbuild reported
  `Expected ")" but found "from"`. Don't use `` `from` ``/`` `to` `` in schema comments.
- Direction contract (D-051): finding subject (`ticket_id`) = relation `from`, `target` = `to`.
  So `blocks` = subject blocks target; `duplicate` = subject is the dupe (archived), target canonical.
- Target resolution deliberately spans the audited set PLUS the far end of every existing relation,
  so a proactive `unlink` of a stale link to an already-archived/closed ticket still resolves its
  target (that ticket is outside the active audit surface). A finding resolving to neither is dropped.
- Added a mechanical safety net: a `link` finding duplicating an existing edge (same from→to→type,
  both orderings for symmetric `relates`) is dropped, so "existing relations are not re-emitted"
  (Done-When #2) holds even if the agent ignores the prompt.
- The shared package has no vitest runner (D-022); relation-type logic is exercised through the
  worker's `audit.spec.ts`.
