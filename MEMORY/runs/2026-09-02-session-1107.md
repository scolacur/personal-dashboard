## 11:30 — PD-650 filed: creating a project through the API mints `T-1` forever

**`POST /api/widgets/task-monitor/projects` does not accept `key`.** Its allowlist is
`slug, name, githubRepo, robotEnabled, color` (`routes.ts:129-149`) and `createProject`
(`store.ts:179`) has no `key` parameter, so the column lands `NULL` — and `nextDisplayId`
(`store.ts:277`) falls back to `const prefix = proj?.key ?? 'T'` (`:281`). There is no PATCH route for
projects, so **nothing in the API can repair it**, and display ids are never re-issued.

Hit it live: the POST returned `"key": null`, and `PG` had to be set with a `sqlite3 UPDATE` over
SSH against the production DB before a single ticket could be created. That workaround was only
safe because `seq` was still 0 — a minute later it would have been rewriting history.

The gap survived the `agent_projects_add_key_seq` migration because **all three existing projects
were seeded, not created through the route**, so nothing ever exercised it. Filed as **PD-650
([bugfix] POST /projects drops `key`, so an API-created project allocates T-1, T-2 forever)** under
PD-465 ([Epic] Misc Minor Bugfixes), P1 by D-080 inheritance, `ready: true`.
