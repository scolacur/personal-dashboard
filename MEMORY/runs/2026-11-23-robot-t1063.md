# [Robot] Show the ticket's loop status on its PR: a live status block (state, Evaluator rounds per lens, history)

**What shipped:** A new `apps/agent-worker/src/jobs/robot/pr-status.ts` — a pure renderer
(`renderStatusBlock`/`upsertStatusBlock`/`currentState`) that turns a ticket's `robot_*` timeline
into a markdown status block delimited by `<!-- robot:status:start/end -->`, plus an updater
(`runPrStatusUpdate`) wired into the robot loop tick (after `pollInReviewPrs`) that re-renders each
open Robot PR's block and writes it back via `gh pr edit` only when it changed. Last-rendered hash
kept in `robot_state` under `pr_status_hash:<ticketId>`.

**Worth remembering:**
- The worktree's login shell starts you in `apps/agent-worker`, NOT the monorepo root. That dir has
  its own `package.json` (name `@dashboard/agent-worker`) with no `verify` script and no workspaces,
  so `npm ci` / `npm run verify` there install only agent-worker deps and the web build later dies on
  a missing `@sveltejs/kit`. Run both from `/data/robot-worktrees/robot-t1063` (use `--prefix`), as
  MEMORY already notes ("Run npm run verify from the repo root").
- The config env var for the repo is `AGENT_WORKER_GITHUB_REPO` (default `scolacur/personal-dashboard`),
  not `GITHUB_REPO`. The board URL base reuses `config.visual.publicUrl` (`DASHBOARD_PUBLIC_URL`),
  the same base the visual comment uses; ticket detail pages are `/devops/tickets/<displayId>`.
- Evaluator "revise" re-queues via a `robot_reactivated` event (reason "evaluator requested changes
  (round N)"), not a distinct type — the state line keys off that. A working phase is rendered as
  "Reworking" when the latest reactivation is newer than the latest hand-off.
- The hash short-circuit means a body a rework *rewrote* (losing the block) is only re-inserted once
  the rework's new events (dispatch/hand-off) change the render — which they always do — so the
  markers-missing path and a stale hash never coincide in practice.
